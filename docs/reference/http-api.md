# HTTP API reference

`maverick serve` runs one HTTP server, built in `create_app`
(`src/maverick/server/api.py`), that serves three audiences at once:

* **panels** fetch frames from `/api/displays/{id}/frame` — see
  [The pull protocol](#the-pull-protocol), which is the part battery devices
  depend on;
* **Home Assistant** posts to `/api/displays/{id}/render`, the escape hatch for
  anyone not using [MQTT discovery](mqtt.md);
* **people** get the setup UI at `/`.

The server binds `server.host` and `server.port` (`0.0.0.0:5000` by default);
`maverick serve --host`/`--port` override them for one run. Everything below is
relative to that address.

A machine-readable description of the same routes is committed as
[`openapi.json`](openapi.json), generated by `scripts/gen_docs.py` from the
running FastAPI application, and served live at `/api/openapi.json` with a
browsable version at [`/api/docs`](#get-apidocs).

## Routes at a glance

Sixteen routes, plus the two FastAPI adds for its own documentation.

| Method | Path | Token | Purpose |
| --- | --- | --- | --- |
| `GET` | `/health` | no | Liveness, version and connection summary |
| `GET` | `/api/panels` | no | The built-in panel catalogue |
| `GET` | `/api/transports` | no | The registered transports |
| `GET` | `/api/displays` | **yes** | Full summary of every configured display |
| `GET` | `/api/displays/{display_id}` | **yes** | The same summary for one display |
| `POST` | `/api/displays/{display_id}/render` | **yes** | Render one display now |
| `POST` | `/api/render` | **yes** | Render every enabled display now |
| `GET` | `/api/displays/{display_id}/frame` | **yes** | The current frame, for a device that pulls |
| `GET` | `/api/displays/{display_id}/preview.png` | no | The current frame as a viewable PNG |
| `GET` | `/api/displays/{display_id}/esphome.yaml` | **yes** | A ready-to-flash ESPHome configuration |
| `GET` | `/api/setup` | no | TRMNL bring-your-own-server handshake |
| `GET` | `/api/display` | no | TRMNL per-fetch metadata |
| `GET` | `/api/auth/status` | no | Which Home Assistant credential is in use |
| `GET` | `/api/auth/start` | **yes** | Begin linking a Home Assistant account |
| `GET` | `/api/auth/callback` | no | Where Home Assistant redirects back to |
| `GET` | `/` | no | The setup UI |
| `GET` | `/api/docs` | no | Swagger UI (FastAPI) |
| `GET` | `/api/openapi.json` | no | The OpenAPI document (FastAPI) |

## Authentication

Authentication is off until `server.api_token` is set. Set it, and the seven
routes marked **yes** above require it; `_require_token` is attached to those
routes alone, and it returns immediately when the configured token is empty, so
an unset token means every route is open.

A client may present the token three ways. They carry the same secret and are
compared the same way — the extra spellings widen how a client may present the
token, not who is let in.

| How | Example |
| --- | --- |
| `Authorization` header, bearer scheme | `Authorization: Bearer s3cret` |
| `Access-Token` header (or `ACCESS_TOKEN`) | `Access-Token: s3cret` |
| `token` query parameter | `/api/displays/kitchen/frame?token=s3cret` |

They are tried in that order: the `Authorization` header first, then
`access-token` and `access_token`, then `?token=`. Header names are
case-insensitive, but a hyphen and an underscore are different characters,
which is why both spellings are accepted — TRMNL firmware sends `Access-Token`
and the bring-your-own-server reference documentation spells the same field
`ACCESS_TOKEN`. The comparison is `hmac.compare_digest`, so a wrong token takes
the same time to reject whatever it gets right.

A missing or wrong token fails the whole request with **401** and:

```json
{"detail": "invalid or missing API token"}
```

One consequence of the list above is worth stating plainly: `/api/displays/{id}/preview.png`
is **not** behind the token, so anyone who can reach the server can see what a
panel is showing. The setup UI and the Home Assistant image entity both use
it, which is why. Treat the server as something to keep on a trusted network
rather than exposed to the internet.

`/api/displays/{id}/esphome.yaml` **is** behind the token: the configuration it
generates embeds `Authorization: "Bearer <api_token>"` verbatim when
`server.api_token` is set (`src/maverick/esphome/generator.py`), so the route
that serves it carries the same `_require_token` dependency as the other
`/api/displays/...` routes. The setup UI's "ESPHome config" link appends
`?token=` itself when the page was opened with one, the same way its fetch
calls send `Authorization: Bearer` (`src/maverick/server/ui.py`).

## Status and catalogue

### `GET /health`

No parameters, no authentication, always **200**:

```json
{
  "status": "ok",
  "version": "0.1.0",
  "displays": 2,
  "home_assistant": false,
  "mqtt": false
}
```

| Key | Meaning |
| --- | --- |
| `status` | The literal `"ok"`. The endpoint is a liveness check: reaching it at all is the signal. |
| `version` | `maverick.app.VERSION`. |
| `displays` | How many displays are **enabled** (`config.enabled_displays`), not how many are configured. |
| `home_assistant` | Whether a Home Assistant client was built, which happens when `home_assistant.token` is set. It does not re-check reachability. |
| `mqtt` | Whether an MQTT publisher exists **and** its connection is currently up. |

### `GET /api/panels`

The built-in panel catalogue, as a JSON array — the same data as
[the panel catalogue page](panels.md) and `maverick panels`. One object per
panel:

```json
{
  "id": "kindle-basic",
  "name": "Kindle 4/Touch (jailbroken)",
  "vendor": "amazon",
  "width": 600,
  "height": 800,
  "color_scheme": "gray16",
  "dpi": 167,
  "supports_partial": false,
  "default_transport": "http_pull",
  "esphome_model": null,
  "notes": ""
}
```

### `GET /api/transports`

The registered transports, sorted by name — see
[the transport reference](transports.md). One object per transport:

```json
{
  "name": "http_pull",
  "pushes": false,
  "description": "Device fetches frames over HTTP (ESP32, ESPHome, Kindle, TRMNL)"
}
```

`pushes` is false for a transport that publishes and waits to be collected, and
true for one that reaches out to the device itself.

## Displays

### `GET /api/displays`

**Requires the token.** An array of display summaries, one per entry in
`displays:` — including disabled ones, so `enabled` is worth reading.

### `GET /api/displays/{display_id}`

**Requires the token.** The same summary for one display. An unknown id is
**404** with the lookup error as the detail:

```json
{"detail": "\"No display 'nope'. Known displays: kitchen, hallway-tag\""}
```

The summary, with every key from `_display_summary`:

```json
{
  "id": "kitchen",
  "name": "Kitchen panel",
  "enabled": true,
  "panel": "waveshare-7in5-mono",
  "panel_name": "Waveshare 7.5\" monochrome (V2)",
  "dashboard": "/lovelace-eink/kitchen",
  "width": 800,
  "height": 480,
  "color_scheme": "mono",
  "dpi": 124,
  "rotation": 0,
  "frame_format": "png",
  "transport": "http_pull",
  "schedule": {
    "enabled": true,
    "every": "5m",
    "cron": null,
    "quiet_hours": "23:00-06:30",
    "on_change": []
  },
  "state": {},
  "checksum": "0123456789abcdef",
  "lint": {"summary": "ok", "issues": [], "metrics": {"coverage.ink": 0.12}},
  "last_pulled_at": null
}
```

| Key | Meaning |
| --- | --- |
| `id`, `name`, `enabled`, `panel`, `dashboard` | Straight from the display's configuration. |
| `panel_name` | The panel profile's display name, resolved from `panel`. |
| `width`, `height`, `color_scheme`, `dpi`, `rotation`, `frame_format` | The **resolved** values: the panel profile's, with any per-display override applied. |
| `transport` | `transport.type` only; the transport's own options are not echoed. |
| `schedule.enabled` | The **live** value — the [scheduled-renders switch](mqtt.md#commands) flips this without touching the config file. The other `schedule.*` keys come from the config. |
| `schedule.every`, `cron`, `quiet_hours`, `on_change` | As configured; `null` or `[]` when unset. |
| `state` | The persisted per-display state, `{}` before the engine has any for this display. Keys: `sequence`, `frames_since_full`, `last_checksum`, `last_render_at`, `last_delivery_at`, `last_error`, `consecutive_failures`, `last_pulled_at`, `render_count`, `skip_count`. |
| `checksum` | The stored frame's checksum, or `null` if nothing has been rendered yet. |
| `lint` | `summary`, `issues` (each with `code`, `severity`, `message`, `hint`) and `metrics` from the last render, or `null` if there is no frame. |
| `last_pulled_at` | When a device last fetched the frame, in this process. It is held in memory, so it is `null` after a restart until the next fetch — unlike `state.last_pulled_at`, which is persisted. |

### `POST /api/displays/{display_id}/render`

**Requires the token.** Renders one display now and waits for the result.

| Parameter | In | Type | Default | Meaning |
| --- | --- | --- | --- | --- |
| `display_id` | path | string | — | The display to render. |
| `force` | query | boolean | `false` | Bypass the unchanged-checksum shortcut and the lint gate, and ask for a flashing full refresh. |

**200** with the outcome:

```json
{
  "display": "kitchen",
  "ok": true,
  "skipped": false,
  "reason": "",
  "render_s": 1.204,
  "total_s": 1.611,
  "checksum": "0123456789abcdef",
  "lint": "ok",
  "delivery": "available at http://maverick.local:5000/api/displays/kitchen/frame"
}
```

| Key | Meaning |
| --- | --- |
| `display` | The display id, echoed. |
| `ok` | Whether the render and its delivery succeeded. A skipped render is also `ok`. |
| `skipped` | True when nothing was delivered — the frame was identical to the last one, or the lint gate blocked it. |
| `reason` | Why it was skipped or why it failed; empty on a plain success. `"frame unchanged"` and `"blocked by lint: …"` are the two skip reasons. |
| `render_s` | Seconds spent screenshotting the dashboard, to three decimal places. |
| `total_s` | Seconds for the whole render, process and deliver cycle. |
| `checksum` | The new frame's checksum, or `null` if no frame was produced. |
| `lint` | The linter's one-line summary, or `null`. |
| `delivery` | The transport's own description of what it did, or `null` if delivery never ran. |

**404** for an unknown display, **401** without a valid token, **422** if
`force` is not a boolean.

### `POST /api/render`

**Requires the token.** Renders every *enabled* display concurrently. Takes the
same `force` query parameter, which is passed through to each display. Returns
an array of the four keys that matter in bulk:

```json
[{"display": "kitchen", "ok": true, "skipped": false, "reason": ""}]
```

## The pull protocol

### `GET /api/displays/{display_id}/frame`

**Requires the token.** This is the endpoint a battery panel lives on, and the
one place where getting the details right is worth real runtime. A device wakes,
asks whether anything changed, draws it if so, and sleeps again.

The response body is the frame itself, in the display's configured
`frame_format`: `image/png` for `png`, `image/bmp` for `bmp`, and
`application/octet-stream` for the raw layouts (`packed`, `planes`, `indexed`).

#### ETag and If-None-Match

`ETag` is the frame's checksum in double quotes: `"0123456789abcdef"` — sixteen
lowercase hex characters, the first 16 of a SHA-256 over the panel's palette
indices (`Frame.checksum`). Hashing what the panel will actually show, rather
than the screenshot behind it, means a re-render that differs only in sub-pixel
noise produces the same ETag and so no refresh.

Send the last ETag back in `If-None-Match`. If it matches, the answer is **304**
with every header below and **no body**. This is the whole point of the
endpoint: a matching ETag means the panel is already showing this frame, so the
304 saves the download and, far more importantly, the e-ink refresh — which is
orders of magnitude more expensive than the request that avoided it.

The comparison is exact, after stripping surrounding whitespace: send the ETag
back verbatim, quotes included. Weak validators (`W/"…"`) and lists of ETags are
not understood.

#### Response headers

Every response carries all of these, on **200** and **304** alike.

| Header | Example | What a device should do with it |
| --- | --- | --- |
| `ETag` | `"0123456789abcdef"` | Store it across deep sleep and send it back as `If-None-Match` on the next request. |
| `Cache-Control` | `no-cache` | Do not serve this from a cache without revalidating. The frame at a fixed URL changes. |
| `X-Maverick-Checksum` | `0123456789abcdef` | The same value unquoted, for firmware with no ETag handling. Compare it with what is on the panel. |
| `X-Maverick-Width` | `800` | Panel width in pixels. Sanity-check it against the display before drawing; a mismatch means the configuration changed. |
| `X-Maverick-Height` | `480` | Panel height in pixels. |
| `X-Maverick-Colors` | `2` | How many inks the frame is quantised to — the palette size. Tells a raw-format client how many bits per pixel to expect. |
| `X-Maverick-Next-Refresh` | `300` | Seconds to sleep before asking again. See below. |
| `Date` | `Sun, 14 Sep 2026 09:04:11 GMT` | The server clock. Firmware can set its time from this and needs no SNTP client. |

`Date` is added by the ASGI server, not by Maverick: the handler deliberately
does not set one, because a duplicate `Date` is invalid HTTP and the minimal
parsers in e-ink firmware are exactly the clients that mishandle it.

`X-Maverick-Next-Refresh` is the display's schedule interval in whole seconds —
`every: 5m` gives `300`. For a display on a `cron` schedule, or with no schedule
at all, it is **900** (fifteen minutes): the time until the next cron run is
knowable, but a device only needs a safe upper bound, and a fixed one keeps the
header cheap. It is a hint, not a contract; nothing rejects a device that asks
sooner.

#### Status codes

| Code | When | Body |
| --- | --- | --- |
| **200** | A frame exists and the ETag did not match. | The frame bytes. |
| **304** | The ETag matched. | Empty. |
| **401** | `server.api_token` is set and the request did not present it. | `{"detail": "invalid or missing API token"}` |
| **404** | Nothing has been rendered for this display yet. | `{"detail": "no frame rendered yet for 'kitchen'; POST /api/displays/kitchen/render first"}` |
| **404** | Unknown display id. | `{"detail": "\"No display 'nope'. Known displays: kitchen, hallway\""}` |

A 404 on a freshly started server is normal and self-correcting: frames are
persisted to disk and restored at startup, and the first scheduled render
publishes one. A device that gets a 404 should sleep and try again rather than
treat it as an error.

Every fetch is recorded, on 304 as well as 200, and surfaces as `last_pulled_at`
in [the display summary](#get-apidisplaysdisplay_id) — which is how you tell a
sleeping panel from a dead one.

#### A minimal client

The whole loop, with the ETag kept across sleep (in RTC memory on an ESP32, in a
file anywhere else):

```text
etag := ""                                  # nothing drawn yet

forever:
    request GET /api/displays/kitchen/frame
        Access-Token: <server.api_token>    # omit if no token is configured
        If-None-Match: <etag>               # omit while etag is empty

    on 200:  draw(body); etag := response.ETag
    on 304:  do nothing at all — the panel is already correct
    on 404:  no frame yet; try again later
    on 401:  the token is wrong; stop and report it

    sleep(int(response["X-Maverick-Next-Refresh"]))
```

The same thing with `curl`, which is the quickest way to check a panel's view of
the server:

```console
$ curl -sD - -o frame.png \
    -H 'Access-Token: s3cret' \
    http://maverick.local:5000/api/displays/kitchen/frame
HTTP/1.1 200 OK
date: Sun, 14 Sep 2026 09:04:11 GMT
etag: "0123456789abcdef"
cache-control: no-cache
x-maverick-checksum: 0123456789abcdef
x-maverick-width: 800
x-maverick-height: 480
x-maverick-colors: 2
x-maverick-next-refresh: 300
content-type: image/png

$ curl -sD - -o /dev/null \
    -H 'Access-Token: s3cret' \
    -H 'If-None-Match: "0123456789abcdef"' \
    http://maverick.local:5000/api/displays/kitchen/frame
HTTP/1.1 304 Not Modified
etag: "0123456789abcdef"
x-maverick-next-refresh: 300
```

## Previews and device configuration

### `GET /api/displays/{display_id}/preview.png`

No token. The last frame as a viewable PNG — the quantised result with the real
inks, not the source screenshot. Used by the setup UI and by the Home Assistant
[image entity](mqtt.md#the-image-entity-two-modes).

**200** `image/png`, with `Cache-Control: no-cache` and the same `ETag` as the
frame endpoint. `If-None-Match` is **not** honoured here: the ETag is published
for cache validation by anything that does its own, but this handler always
sends the body. **404** with `{"detail": "no frame rendered yet"}` when there is
no frame, or a frame with no preview.

### `GET /api/displays/{display_id}/esphome.yaml`

**Token required.** **200** `text/plain` containing a complete ESPHome YAML
document for this display: the panel model, the display buffer, and an
`online_image` pointing at this display's frame URL with the refresh interval
already filled in. **404** for an unknown display. When `server.api_token` is
set, the generated document embeds it as an `Authorization: Bearer` header
(`src/maverick/esphome/generator.py`), so the route carries the same
`_require_token` dependency as the other authenticated `/api/displays/...`
routes — otherwise an unauthenticated request to this route would hand back
the very token that gates every other endpoint.

## TRMNL (bring your own server)

Two routes implement the TRMNL BYOS handshake. Both identify the device by the
MAC address the firmware sends in the **`ID`** header; no other header is read,
and the token check does not apply to either route. The MAC is uppercased and
hyphens are treated as colons, so `a4-cf-12-34-56-78` and `A4:CF:12:34:56:78`
match the same display.

Matching is against a `mac` key in the display's `transport` block, which any
transport accepts because transport options are open-ended:

```yaml
displays:
  - id: hallway
    panel: trmnl-7in5
    transport:
      type: http_pull
      mac: A4:CF:12:34:56:78
```

A TRMNL panel needs nothing else.

### `GET /api/setup`

Called once, when the device is claimed. **200**:

```json
{
  "status": 200,
  "api_key": "s3cret",
  "friendly_id": "HALLWA",
  "image_url": "http://maverick.local:5000/api/displays/hallway/frame",
  "message": "welcome to maverick"
}
```

| Key | Value |
| --- | --- |
| `status` | The literal `200`, repeated in the body as TRMNL expects. |
| `api_key` | `server.api_token` if set, otherwise the display id. The firmware stores this and sends it back as `Access-Token`, which is why the frame endpoint accepts that header. |
| `friendly_id` | The first six characters of the display id, uppercased. |
| `image_url` | `server.base_url` + `/api/displays/{id}/frame`. With `base_url` unset this is a bare path, which the firmware cannot resolve — set `server.base_url`. |
| `message` | The literal `"welcome to maverick"`. |

An unmatched MAC gives HTTP **404** and
`{"status": 404, "message": "no display for MAC A4:CF:12:34:56:78"}`.

### `GET /api/display`

Called on every wake, before fetching the image. **200**:

```json
{
  "status": 0,
  "image_url": "http://maverick.local:5000/api/displays/hallway/frame",
  "filename": "hallway-0123456789abcdef",
  "refresh_rate": 900,
  "reset_firmware": false,
  "update_firmware": false
}
```

| Key | Value |
| --- | --- |
| `status` | The literal `0` — TRMNL's "nothing wrong" code, not an HTTP status. |
| `image_url` | The frame URL, as above. |
| `filename` | `{display id}-{checksum}`, or `{display id}-pending` when nothing has been rendered yet. The firmware treats it as the image's identity, so it changes exactly when the frame does. |
| `refresh_rate` | Seconds until the next fetch — the same value as `X-Maverick-Next-Refresh`. |
| `reset_firmware` | Always `false`. |
| `update_firmware` | Always `false`. |

An unmatched MAC gives HTTP **404** and `{"status": 404}`.

The device then fetches `image_url` itself, with its stored key in the
`Access-Token` header. That fetch is [the pull protocol](#the-pull-protocol)
like any other, 304s included.

## Linking a Home Assistant account

Rendering a dashboard needs a credential that authenticates a *frontend*
session, because Maverick loads the real dashboard in a browser rather than
redrawing it from entity states. These three routes obtain one through the
IndieAuth flow Home Assistant's companion apps use, so nobody has to copy a
long-lived token by hand. The mechanism is in `src/maverick/ha/auth.py`.

### `GET /api/auth/status`

What credential Maverick currently holds, and whether linking is even possible.

```json
{
  "linked": false,
  "kind": "none",
  "connected": false,
  "url": "http://homeassistant.local:8123",
  "can_link": true,
  "reason": "",
  "client_id": "http://192.168.1.10:5000/",
  "persists": true
}
```

`kind` is `long-lived token`, `linked account` or `none`. `can_link` is false
when `server.base_url` is unset or is not an http(s) URL, because Home
Assistant has to redirect back to it; `reason` then says so. `persists` reports
whether Maverick is running as a Home Assistant app and can therefore save
the credential to its own options.

### `GET /api/auth/start`

Returns the URL to send the browser to. Behind the API token, because starting
a link is a privileged action.

```json
{"authorize_url": "http://homeassistant.local:8123/auth/authorize?client_id=..."}
```

`client_id` is `server.base_url` normalised to scheme, host and `/`;
`redirect_uri` is `/api/auth/callback` on that same origin. Sharing an origin
is what lets Home Assistant approve the redirect without fetching anything.
Home Assistant accepts a local IP address as a `client_id` host, so the default
`base_url` works.

Returns `400` when `server.base_url` is unset or unusable.

### `GET /api/auth/callback`

Where Home Assistant sends the browser back, with `code` and `state`. Exchanges
the code for a refresh token, applies it without a restart, and saves it to the
app options when running under the Supervisor. Responds with a small HTML page,
not JSON — a browser lands here, not a script.

This route is **not** behind `server.api_token`, and cannot be: Home Assistant
knows nothing of that token. The `state` nonce authenticates it instead. It is
minted by `/api/auth/start`, which *is* behind the token, and it is spent on
first use, so a callback Maverick did not start is refused.

## The setup UI

### `GET /`

With `server.enable_ui: true` (the default) this is the setup and monitoring
page: one card per display showing the current frame, the resolved geometry, the
schedule, the lint findings, buttons to render and full-render, and a link to
the display's generated ESPHome configuration. It is a single self-contained
HTML page — no build step, no dependencies, no polling.

The page itself is unauthenticated, but the requests it makes are not. When
`server.api_token` is set, open the UI as `http://host:5000/?token=<token>`: the
page reads `token` from its own query string and sends it as
`Authorization: Bearer` on the render calls.

With `server.enable_ui: false` the route still answers **200**, with a one-line
page pointing at `/api/docs`. Turning the UI off does not turn off the API, and
does not affect the preview images, which are what the cards display.

### `GET /api/docs`

FastAPI's Swagger UI over `/api/openapi.json`, for trying routes by hand. Both
are served whatever `enable_ui` says, and neither is behind the token — the
document describes the routes, it does not grant access to them. The committed
copy of that document is [`openapi.json`](openapi.json); regenerate it with
`python scripts/gen_docs.py` after changing a route.

## Error responses

Every error is JSON with a `detail` key, FastAPI's convention, except the two
TRMNL routes which return their own shape.

| Code | Meaning |
| --- | --- |
| **401** | `server.api_token` is set and the request presented no token or the wrong one. Only the five authenticated routes can return this. |
| **404** | Unknown display id, or no frame rendered yet. The detail says which. |
| **422** | A parameter failed validation — in practice a `force` query value that is not a boolean. The detail is FastAPI's validation-error array. |
